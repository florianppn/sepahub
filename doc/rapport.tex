\section{Introduction}

Ce projet porte sur la réalisation du service REST SEPA26 et de son interface Web. L'objectif est de construire une architecture basée sur la norme ISO 20022 (prélèvement SEPA Direct Debit, format \texttt{pain.008.001.02}) fournie en cours pour gérer des transactions bancaires. Le déploiement est entièrement conteneurisé et orchestré via Docker Compose (Frontend Angular, Backend Spring Boot et Base de données MariaDB).

\section{Architecture du Projet}

L'application est structurée selon un modèle classique en couches (Layered Architecture), garantissant une stricte séparation des responsabilités conformément aux principes SOLID et DRY.

\subsection{Organisation Logicielle}
L'application suit une architecture en couches, dont voici les responsabilités principales :
\begin{itemize}
    \item \textbf{Couche de Présentation (API REST) :} Gère les requêtes HTTP via des contrôleurs REST stricts (\texttt{@RestController}), assure le rendu en XML (JAXB) et JSON (Jackson), la transformation HTML via XSLT (Saxon-HE), et la normalisation des réponses d'erreur via un gestionnaire global (\texttt{@RestControllerAdvice}).
    \item \textbf{Couche de Service :} Centralise la logique métier SEPA, orchestre la validation technique et métier, et délègue les transformations XML à des services spécialisés.
    \item \textbf{Couche d'Accès aux Données :} Assure la persistance relationnelle via Spring Data JPA et MariaDB.
    \item \textbf{DTO \& Utilitaires :} Facilitent le transfert de données, l'adaptation temporelle et les transformations XSLT.
\end{itemize}

\subsection{Stack Technique}
Le service repose sur une stack Java 25 moderne et robuste :
\begin{itemize}
    \item \textbf{Framework :} Spring Boot 4 (Spring Web, Spring Data JPA).
    \item \textbf{Gestion des dépendances :} Maven.
    \item \textbf{Stockage :} MariaDB 11 (Production/Docker) et H2 (Environnement de test).
    \item \textbf{Traitement XML :} JAXB (Jakarta XML Binding), Jackson-XML et Saxon-HE (moteur XSLT 2.0/3.0 et XPath).
    \item \textbf{Interface Frontend :} Angular 22 (Application Single Page autonome servie par Nginx).
\end{itemize}

\section{Patrons de Conception}

Pour améliorer la lisibilité, la modularité et la maintenabilité du backend, trois patrons de conception du Gang of Four (GoF) ont été mis en place : le \textbf{Builder}, l'\textbf{Abstract Factory} et la \textbf{Chaîne de Responsabilité}.

\subsection{Patron Builder (Monteur)}

\subsubsection{Motivation}
Un document SEPA ISO 20022 comporte de nombreux objets imbriqués. Le patron \textbf{Builder} permet de décomposer l'assemblage de ce document complexe en étapes atomiques explicites, sécurisées par un contrôle d'état strict (\textit{fail-fast}). Il masque la complexité technique d'instanciation, bannit les structures de classes internes parasites, garantit des valeurs par défaut conformes au standard bancaire et calcule automatiquement le nombre d'opérations et la somme de contrôle financière.

\subsection{Patron Abstract Factory (Fabrique Abstraite)}

\subsubsection{Motivation}
Dans la conception originale du GoF, le patron \textbf{Abstract Factory} opère en synergie naturelle avec le patron \textbf{Builder} : la fabrique est spécialisée dans l'instanciation technique des familles de sous-nœuds XML ISO 20022 (\texttt{Party}, \texttt{Account}, \texttt{Agent}, \texttt{Mandate}, \texttt{AccountSchemeId}), tandis que le monteur se focalise exclusivement sur le séquençage et la validation d'état. Cette séparation isole les détails JAXB et respecte le principe de responsabilité unique (SRP).

\subsection{Patron Chain of Responsibility (Chaîne de Responsabilité)}

\subsubsection{Motivation}
Lors de la réception d'un flux SEPA, plusieurs vérifications successives sont nécessaires (schéma XSD, syntaxe XML, unicité de l'identifiant et cohérence de la somme). La \textbf{Chaîne de Responsabilité} isole chaque règle dans un maillon dédié et testable unitairement, tout en interrompant le traitement dès la première anomalie détectée (\textit{fail-fast}).

\subsubsection{Correspondance des Acteurs}
Le tableau suivant présente le rôle de chaque classe dans la chaîne de validation :

\section{Description de l'architecture Docker et Déploiement}

Afin d'assurer un déploiement fluide, reproductible et moderne du service SEPA26, l'architecture s'appuie sur une conteneurisation complète orchestrée par \texttt{Docker Compose}.

\subsection{Architecture Multi-Services}
Le projet est découplé en trois services autonomes communiquant au sein d'un réseau privé Docker (\texttt{sepa-network}) :

\begin{itemize}
    \item \textbf{Base de données (MariaDB) :} Conteneur MariaDB 11 initialisé automatiquement avec la base \texttt{sepa26\_db} et un utilisateur dédié. La persistance des transactions est garantie par un volume Docker nommé (\texttt{mariadb\_data}).
    \item \textbf{Serveur Backend (Spring Boot 4 / Java 25) :} Conteneurisé via un \texttt{Dockerfile} multi-stage. Une première étape compile le projet avec Maven dans un conteneur dédié, puis l'artefact JAR est injecté dans une image alpine minimale avec le runtime Java 25 Temurin. Le service est lié dynamiquement à la base via les variables d'environnement (\texttt{DB\_URL}, \texttt{DB\_USER}, \texttt{DB\_PASSWORD}).
    \item \textbf{Frontend (Angular) :} Application Single Page (SPA) développée en Angular, compilée puis servie par un conteneur Nginx. Nginx intègre également une configuration de reverse-proxy qui redirige les appels \texttt{/sepa26/*} vers le backend Spring Boot, éliminant tout besoin de configuration CORS dans le code Java.
\end{itemize}

\subsection{Sécurité et Isolation Réseau}
L'architecture Docker privilégie la sécurité :
\begin{itemize}
    \item \textbf{Isolation réseau :} Grâce au réseau bridge \texttt{sepa-network}, la base de données MariaDB communique de manière sécurisée et privée avec le backend Spring Boot.
    \item \textbf{Transparence et Reverse Proxy :} Les clients accèdent au frontend sur le port 4200. Nginx achemine en interne les requêtes d'API vers le backend sur le port 8100.
\end{itemize}

\subsection{Maintenance et Cycle de Vie}
Grâce à \texttt{docker-compose}, la gestion du cycle de vie de la plateforme est simplifiée :
\begin{itemize}
    \item \textbf{Démarrage complet :} \texttt{docker compose up --build -d} compile et démarre l'ensemble des conteneurs en respectant l'ordre de dépendance (la base de données démarre en premier avec vérification de son état de santé).
    \item \textbf{Arrêt des services :} \texttt{docker compose down} stoppe proprement les conteneurs tout en préservant le volume de données.
    \item \textbf{Consultation des logs :} \texttt{docker compose logs -f} permet de suivre les flux d'exécution en temps réel.
\end{itemize}
